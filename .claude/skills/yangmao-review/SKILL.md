# 羊毛审核

目标只有一个：**一条羊毛审一次，网站所有栏目、统计和推送都一次正确，不返工。** 管理员最反感的是“顾头不顾腚”——改了标题忘了日期，补了日期忘了美元，过两天又在别的栏目发现问题。每次审核都核对完整规格，但核对不等于重新生成。已批准字段是基线；官方权益和政策未变时，不因措辞、分类推断、估值或抓取日期变化而改写，不让同一活动换 ID 再上架。

## 先读这些（都在项目里，以它们为准）

- `docs/data-contract.md`：每个字段喂哪些栏目、哪些缺了会拦截。审核前必须知道“这个字段影响哪里”。
- `pipeline/platform-notes.md`：各平台的特点（怎么拆条、用什么单价折算、以哪个渠道为准、哪些只能实测）。`show` 命令会自动打印该平台那一节。
- `pipeline/learned-rules.md`：管理员历次纠正归纳出的通用规则。
- `docs/operations.md`：当前命令、角色权限和发布检查。设计文档的历史决策不能覆盖数据合同和最新规则。

辅助脚本（在项目根目录运行，管理员密钥从 `.prod.secrets` 读取，绝不打印）：

```bash
S=.claude/skills/yangmao-review/scripts/offer.ts
npx tsx $S queue 30                       # 待审列表，拦截项多的在前
npx tsx $S show <短码或ID>                # 全部字段 + 上架前检查 + 修订 + 平台要点 + 信源
npx tsx $S plan <短码> patch.json         # 试算改后的检查结果，不写入
npx tsx $S apply <短码> patch.json --version <reviewVersion> --reason "理由" [--code wrong_field] [--approve] [--dry-run]
npx tsx $S memo <短码> memo.txt           # 内部核验记录（仅管理员可见）
npx tsx $S approve <短码> --version <reviewVersion>
npx tsx $S reject <短码> --version <reviewVersion> --code <代码> --reason "理由"
npx tsx $S retest <短码>
npx tsx $S reopen <短码> --version <visibilityVersion> --reason "明确重开依据"  # 只新建恢复审核，不直接发布
npx tsx $S unpublish <短码> --version <visibilityVersion> --code <代码> --reason "理由"   # 撤下已上架但不该收的条目（对已上架条目用 reject 只会丢弃更新提案）
npx tsx $S suggest <短码> approve|history|reject|judge [--code 代码] --reason "理由"   # 只给审批卡片标建议，不改状态（批量预审用）
```

`patch.json` 只写要改的字段（字段名见 data-contract 第二节）；`evidence` 可以只写要改的部分，比如 `{"evidence":{"tier":"tested"}}`，脚本会和现有证据合并。

## 流程

### 1. 读条目
`show` 拿到全部字段、上架前检查（必须补 / 建议补 / 可选，每条写着影响哪些栏目）、平台要点和已登记信源。用户贴截图时，先从截图里认出短码或标题。

### 1a. 修改前先过稳定性与重复检查
按 [审核稳定性检查](references/review-stability.md) 执行，**在 plan、apply、suggest、approve 或补录之前**完成：
1. 区分公开的已批准原版与待审候选；读取具体字段的增删改、人工修订、通过/拒绝理由及被拒提案。同一个条目被拒更新，不代表旧版被拒。
2. 在全部状态中查相同权益，包括已上架、待审、拒绝、结束以及其他平台归属的记录。比较实际发放/调用平台、权益与模型、领取机制、资格及活动窗口；短码、标题、URL、公告发布者不同不证明是新活动。
3. 每个拟改字段列出“已批准值 → 候选值 → 官方实际变化或管理员纠错依据”。旧摘录没匹配到不等于政策改变；多语言、截句扩句及数字格式先按同版排查，固定X/status按同一公告处理。当前原文再次支持旧值、仅新发现来源或模型换了表述时，保留旧值；补证不自动重审，也不重新估值。用户明确授权V1迁移/重估或管理员明确纠错时，可在授权范围更新估值，保存旧值、公式和依据到内部记录与修订，保持审批及原权益证据时间。
4. 选择处理：无变化＝不写入；纯漂移提案＝按授权拒绝更新并保留旧版；重复新条目＝按授权拒绝重复项并指明主条目；真实条款变化/明确人工纠错＝沿用主 ID、最小补丁、保持待审；独立新轮次才新建。
5. 重复关系必须记录关联编号：对已拒绝对象重报、与已上架对象重复等情况，按稳定性检查的关联记录要求查询并写明本次及相关对象的线索号、条目完整ID、短码、状态与重复依据；只写标题或“重复”不算完成。关联记录仅写内部，不扩大批准/拒绝授权。

缺少原版/历史时先补读，不能把候选当基线或按当前标题另建。不因工具查重未命中就认定不是重复；网络失败不证明原条款消失。拒绝过的同版条款不得靠换标题、ID、URL、日期后重新提审。真正新的官方权益、资格、窗口或管理员明确要求重新审查，可以重开；内部记录说明新依据与上次拒绝原因如何解决。

### 2. 核实——以发放方自己的说法为准
- **谁发放，就找谁的原文**：福利由哪家平台发放，就到那家平台的官网、价格页、帮助文档、博客、更新日志、官方公众号或官方 X 找条款。合作方的新闻稿（比如 OpenAI 写 Replit、腾讯混元写 GMI Cloud 的试用）只是线索：宣传稿会省掉门槛和限制，只有发放方有义务把条款写清楚。平台也要归到发放方。
- **看日期**：博客、更新日志、新闻里的活动先看发布日期。别把几个月前的内测或限时活动当成现行的（LongCat 2.0 内测、MiniMax Agent 旧文都栽过）。已经结束的不是废数据，见第 4 步。
- **读全文，不只读摘录**：价格页的脚注、FAQ、公众号的配图里常有关键条件（如“1 个月内回归的老用户”、可用模型、有效期）。
- **官方没有文字公告、但管理员亲测领到过**的（比如只在客户端弹窗里出现的赠金），证据级别用 `tested`（管理员实测），链接可以是官网下载页。只有管理员确认亲测过才能用这个级别。
- 能直接抓取的页面用 `curl` + 去标签；靠脚本渲染的用 `https://r.jina.ai/<url>`；搜不到入口时用网络搜索找官方页面地址。

### 3. 按规格把字段一次填对

通用全局活动周期（2026-10-11）：有周期原文和已核实开始日/公告时间时，不限一周，分钟/小时/天/周/自然月/自然年及复合周期均由采集草稿与入库共享规则自动填写claimEnd及endKind=date；自然月不等于30天，月底无对应日取月末；evidence.claimEndDerivation保留声明、来源、时间锚点及精度，显示截止估算。个人领取后的有效期是creditValidity；标题、抓取日及只有月份不能当锚点。无绝对日期时不要手算补午夜ISO，摘录周期交程序推算；保存或批准前核对自动推算结果，批准基线沿稳定性规则处理。

2026-10-11管理员网络门槛口径：国外厂商所有活动、国内厂商国际版/全球版必须包含 `net`，移除 `none`，保留其他资格与 `unknown`；仅国内产品且没有其他门槛才允许 `none`。按实际领取产品/入口识别版本，不以语言、X公告或域名后缀代替判断。“无需信用卡”只证明不需要 `card`，不能据此写 `none`。这一统一展示规则不是官方条款变更，内部保留管理员纠错依据，审批状态与官方核验日期不变。

会员资格按选择式目录录入：先读 `GET /api/admin/memberships` 取得当前目录修订号，使用 `membershipRequirement` 选择产品/套餐、任一/全部关系及限制；通过脚本用 JSON 补丁传同一结构。目录缺项先新增待核实项并独立核实。`requirements` 的 member: 文字由服务端生成，不能手工改写覆盖确认结构。旧条目资格解释不清时保存needs_review草稿，不能猜套餐或删除限制后通过；修改其他字段时不传会员字段。保存或批准遇目录版本变化须重新核对，不能刷新版本后盲目重放。
逐项核对，仅修改有独立依据的字段。不得用本表的推断或折算默认值覆盖已经批准的口径；缺字段也先查人工取舍，不把检查提醒当成改写授权：

**公开字段按用户视角写**：title、valueText、steps、creditValidity只写权益、领取操作、实际资格、费用与期限。核验经过、旧记录误归/误估、来源缺口、重复判断、审批待办和估值取舍写内部reviewMemo或审核理由，不能写进简介、步骤或公开adminNote。未知数值/资格仍保留空值、unknown及证据门槛，不能润色成确定承诺。入口不可用、已领完、绑卡、地区限制及自动续费等用户需要知道的事实保留。迁移旧文案时保留内部记录，并检查原条目和待审更新两份文案，审批状态不变。

**估值V1（2026-10-09）**：按 `src/shared/valuation.ts` 与 `docs/plans/benefit-valuation-and-field-completion-v1.md` 核对。公开计算区可放价格来源、计费单位、公式、标准用量、基准模型、覆盖和必要假设；reviewMemo保留问题、旧值、纠错及审核待办。管理员reviewed valuation与对应美元受抽取保护，不因新抽取清空或重新计算。只有本次授权重估/迁移或明确人工纠错才覆盖旧值；价格核验时间不是权益lastVerifiedAt。

**估值V2（2026-10-11）**：新研判按 `docs/plans/benefit-valuation-and-field-completion-v2.md`，旧V1仍兼容。管理员明确采用入门/指定套餐、候选算法、第三方数量或替代模型时，保留来源与必要假设，新增benchmarkType并标provisional；不得把价格参照当真实官方面额、积分兑换证明或保证申请额度。通常用正常月价，指定年价另除12；有两种适用算法取低值。特殊用量倍率仅用于指定场景，单卡价先算再乘实际张数。不可估值按null结案，不写零。拒绝、合并、历史化另按明确的逐条授权与版本锁执行。

**V2自动核算（同日新增授权）**：线上agent提取原文因子，`valuation-engine.ts`与`valuation-intake.ts`计算并验证价格、币种、单位、模型、期限及共享池；可信价格目录有日期，过期价格页与ECB由采集流程补抓。管理员已审元数据、旧人工美元及人工提案持续保护，带自动标记的估值一经人工编辑同样按修订保护。自动计算不批准条目；缺价、访问失败与来源不一致保持待核实。人工审核可复核程序公式，不需手算重写金额。

| 标签 tags | reset 额度重置 / referral 邀请奖励 / discount 首月或限时折扣 / daily 每日刷新或每日登录送。 |
| 额度有效期、领取步骤 | 中文；步骤写清楚在哪、点什么。 |
| 证据 evidence | 首次批准须有发放方官方链接 + 级别（site / docs / official / staff / tested）+ 原文逐字摘录（权益、资格、有效期），原文保留原语言。摘录应是页面上连续的一段，不拼接、不改写、不跨加粗或链接，便于首次审核和后续真实条款变更比对；已批准条目不定期重抓旧证据，旧网页改写不撤销批准。证据级别是 media 时服务器一定拒绝，即使检查清单显示“拦截 0”：官方页面因正文短被走 Jina 降级的，核实后改回 docs / site。 |

**厂商与渠道双公告去重**：同一限免活动可能由调用平台和模型厂商各公告一次；以实际提供免费调用/领取的渠道为平台归属，以模型/权益、活动窗口和领取机制确认同一事件，不能按发帖账号、转发时刻或厂商时区新建另一活动。厂商转述只补来源，追查调用平台原文；已有条目沿用其ID。不同渠道各自提供同一模型时，分别核验其条件并归各渠道，不能按模型名把所有渠道合并。只有明确不同轮次、窗口或发放机制才独立建条目。

**厂商旗下产品与第三方平台分清**：先核实公司归属，再核实权益实际发放产品。Qoder和Qwen/Qwen Code同属阿里体系，不能把Qoder当独立第三方厂商；Qoder与Qwen Code又是不同产品，不互套额度。平台名称标明已核实的厂商，platformId仍按发放产品及领取机制记录；同集团不等于余额通用。同一活动的厂商/旗下产品双公告去重，区域产品分开核验当前条款；第三方平台调用Qwen模型不因此成为阿里产品。

**拆条和归属**：同一活动多模型或多档加赠合一条；同一平台独立的领取渠道或活动要分开写（如 OpenCode 应用内免费 / Zen API 需绑卡 两条；Go 套餐本身不收；硅基流动实名礼和推荐官两条），各自列模型。平台不在白名单或重复登记的（如 LiblibAI 与 LibTV 是同一平台），先在 `seed/platforms.json` 处理白名单。官方只在公众号发公告的平台，在 `seed/platforms.json` 给平台写 `wechat`（公众号名），线上同步改 platforms.wechat，否则公众号文章过不了证据检查。

**摘录自检**：每段摘录都要是证据页上连续的一句原文（复核会把标签换成空格后比对）。不要用分号拼表格行，不要摘脚本渲染的价格卡片，跨加粗或链接就换一句；写完用 curl 或 Jina 抓证据页确认这句原样存在。

### 4. 决定去向
- **消费促销不收（2026-10-09）**：消费返利/返现、累计消费达标、首购/升级付费/充值后送积分、Token或奖金，不因限时、额外发放或翻倍而收；拒绝other，已上架用unpublish。覆盖旧topup收录例外；邀请注册奖励与付费升级奖励混在一起时只收无需消费的部分。订阅重置和身份认证资助按各自规则。
- **重置时间与去重**：Codex / ChatGPT 重置按官方每次发放的实际语义记录，不按同名/同额度去重。单次自动重置或banked reset卡发放：claimStart与claimEnd为同一事件日；publishedAt保存Tibo（@thsottiaux）官方原公告精确时间，process/传播进度回复不能冒充新发放。明确tomorrow或指定执行日时，事件日按原文，发布时间另存；卡的使用期限不扩成发放窗口。若明确未来24小时重置两次、未来一周每天重置等多次安排，则保留公告覆盖的起止区间，不强制同日；new release、未来改进、next week本身不是持续重置证据。不同时间点的独立发放，即使同一天也可分别记录；同一次发放的预告、确认、延迟解释仍为同一事件，不能只按推文时间不同判成新福利。只有窗口明确才计算日期，不猜未公布的逐次process时刻。
- **比赛获奖奖励不收**：比赛、竞赛、黑客松及排名/投票评选的获奖奖励不纳入收录；即使奖品是 AI 积分、Token 或会员，也不是用户可领取的羊毛，不作为会员福利或申请制输出。只面向获奖者的奖池、奖金和名次奖励按 other 拒绝；同页独立的、无需获奖即可领取的注册/参赛赠额另按其条款审核。科研、教学、创业及创作者申请制资助不因人工评审而自动视为比赛，仍按资助规则核验。
- **通过**：核实属实、字段齐、没有拦截项。
- **补字段后通过**：大多数情况。
- **只收现行权益（2026-10-22，取代“已结束但属实作为历史上架”）**：截止日早于本月 1 日（来源时区）的活动按 expired 拒绝；本月内刚结束的仍可补准日期后通过。发布较早但仍在进行的照常审核，不能因发布时间早判过期。例外：Codex 额度重置按专用流程照常收录；管理员明确要求补录的历史活动按其指示处理。已上架的历史条目保留。
- **拒绝**：不属实、不在收录范围（非 AI 额度、付费套餐自带权益、单纯定价或打折）、重复、平台归错且无法改正。理由代码选准，理由写清楚，模型会从拒绝理由里学习。expired 用于截止早于本月的已结束活动，以及日期实在无法确认的旧活动。
- **会员档位本身的权益不是羊毛**：价格页里各订阅档“每月多少积分、可用哪些模型、无限量”都是买套餐买到的，按“付费套餐自带”（paid_bundle）拒绝。可收的是可量化免费额度、订阅档额外的额度重置、常规套餐之外的加赠（如智谱加赠的重置卡、多送的 Token、限时翻倍）。几个档位有同一种加赠时合成一条，各档新增权益按V1分别解释，不能用最高档冒充人人可得或整个订阅价充当重置价值。
- **“加赠/限时”不是独立活动的充分证据**：套餐表的基础积分、加赠积分和每月实得可能只是当前分档定价；WorkBuddy 三档每月加赠不收，也不合并为一条。须核实独立活动条件或赠送机制，再判断套餐外赠额；积分到账后有效期不是活动截止，抓取失败或缺截止不证明活动不存在。
- **区分账单模式和先付款**：AWS Paid plan 的 Free Tier 可有免费服务额度；Paid plan 无固定订阅费。只要求启用按量计费并绑定支付方式、不要求先付款时，不标 pay；保留实际支付方式门槛及正文中的超额收费条件。
- **补字段时保留单位与来源边界**：Vidu 注册礼一次性 20 积分、Q4 每秒扣费和参考素材月配额分开，不把 references 写成视频生成次数；亲测数量不能拼进官网原文。创业赠金、会员和合作方优惠分开估值；月份、扩展日期和领取后有效期分别写，不猜具体日。具体数值和资格看平台要点及最新官方来源。
- **认证专享大幅优惠要收**：学生、教师、设备持有人（买 Pixel 送 Google AI Pro）等身份认证后才有的免费会员或五折及以下的折扣算羊毛（如 Google AI Pro 学生 12 个月、Mistral 学生价约四折、Copilot 教师免费 Pro）；八折这种小折扣仍不收。
- **免费套餐本身不收**：模型公司和 AI 产品免费版的有限聊天、搜索、生图（只写 limited / generous limits）是价目里的 Free 档，不是羊毛；只收免费档里附带的可量化额度（如 Mistral 每月 $10 API credits）。门槛按“要用上这份额度必须做什么”写，要先绑卡充值 API 的写 card + pay。
- **首月优惠不收**：首月几折、新用户首月半价这类订阅折扣很常见，不是免费额度，按 other 拒绝；例外是首月实付不超过 $1（约 ¥7）、基本等于免费的（如 ElevenLabs Starter 首月 $1），保留并打 discount 标签。价目表上“充值多送”的常设阶梯价也不收。
- **不是 AI 额度**：云厂商的数据库、容器、BI、云服务器、直播点播、API 网关等产品试用按 not_ai 拒绝。付费档的 Relax / Explore / 无限量模式、常设的“订阅多送 X%”按 paid_bundle 拒绝。
- **多档位折美元**先确认赠额与购买积分的单位、资源和使用模式等值，再取适用档位最低“套餐价 ÷ 积分”费率，有加量包单价优先。不同套餐同名 credit 或统一账本不证明美元面值相同，缺少对应关系留空；reset 标签只给订阅额度重置事件，每月固定次数不打。

### 5. 先试算，再给管理员方案
完成第 1a 步后，把最小修改写成 patch.json，用 `plan` 试算，说明剩余拦截和提醒。无实际差异时不生成补丁、不 apply，也不重复 suggest/approve；没有字段拦截不代表不是重复或可以重上架。按本次授权执行：管理员已要求“核实完直接修改，上架由我批”时，直接补字段并写内部记录，保持待审；不能把补字段当通过。只有管理员明确要求先给方案时，按下列格式展示后等待确认；上架始终需要明确授权。

```
## [短码] 标题（平台）
**结论**：建议 通过 / 补字段后通过 / 拒绝（理由代码：…）
**核实**：官方出处 <链接>，关键原文「…」；和当前条目的出入：…
**要改的字段**
| 字段 | 现在 | 改为 | 依据 |
**改后的上架前检查**：拦截 0 · 提醒 N（剩下的提醒及影响的栏目、为什么暂时补不了）
**核验记录（内部）**：核验程度；如果是漏抓，写明漏抓原因
**要沉淀的**：平台要点 / 通用规则（没有就写“无”）
按本次授权说明已补字段、待批或等待方案确认；不要重复索要已有授权。
```

批量审核时每条一个小节，最后汇总：建议通过几条、拒绝几条。

### 6. 按授权写入并读回
1. 写入前重新读取 `reviewVersion` 和差异，确认仍是刚审核的版本；发生并发变化重新比较，不能覆盖新人工修改。使用管理接口写 edit/approve/reject/unpublish/withdraw 时带 `expectedReviewVersion`（辅助脚本的 apply/approve/reject/unpublish 强制要求 `--version`，取自完成审核时的 show；下架/撤回使用 visibilityVersion，提案审核使用 reviewVersion；不要改为提交前自动取最新版）。
2. `apply <短码> patch.json --version <reviewVersion> --reason "…" [--approve]`：理由写清楚为什么这样改（模型以后学得更快）；改类型用 `--code wrong_type`。
3. `memo`：写内部核验记录（核验程度、证据来源、截图位置、漏抓原因）。
4. 字段已齐且获得首次上架或真实变更批准授权时用 `approve`；拒绝更新与拒绝新条目用 `reject`，已上架误收要用 `unpublish`，不能删主条目逃避历史。`retest` 仅记录确已核实仍有效，不用于绕过证据拦截；管理员亲测权益与人工读官网是两回事。
5. 再 `show` 一次，确认审核状态和检查结果符合预期。服务器拒绝时，原样把原因告诉管理员，不要绕过。

### 7. 沉淀
- 这次的判断里，有某个平台特有的东西（拆条方式、折算单价、以哪个渠道为准、只能实测），写进 `pipeline/platform-notes.md` 对应平台一节。
- 对所有平台都成立的，写进 `pipeline/learned-rules.md`。
- 改了文件就提交（commit message 末尾加项目约定的署名行），在回复里说一句写进了哪里。

## 管理员说“这条漏抓了”时
顺着链条查到底，修在源头：平台在不在白名单 → 有没有配信源、信源页面能不能读到正文（脚本渲染的走 Jina）→ 关键词有没有把句子筛掉 → 模型有没有输出（提示词是否让它放弃）→ 输出是否因字段不合规被丢弃。补录条目时按本流程走完，并在核验记录里写明漏抓原因和已补的措施。

## 别做的事
- 不打印、不外发管理员密钥；不改 `.prod.secrets`。
- 超出管理员授权写入、通过或拒绝；已有直接修改授权时不重复要求确认，上架和拒绝仍需对应授权。
- 只改用户点名的字段而不看检查清单；或反过来把全字段核对变成全字段重写。
- 因抓取时间、译文、字段顺序、金额格式、不同公告 URL、同一集团不同品牌或日期后缀而重复提交/新建；把 rejected、旧版或主 ID 隐藏掉再提审。
- 用合作方新闻、第三方汇总站当证据；自己编单价或使用次数。
- 把仍在进行的旧帖活动当作已结束拒掉，或因发布时间早就判过期。

## 技能回归与中央库同步

`evals/evals.json` 包含审核场景与断言，执行模型评测时使用合成场景，不操作真实生产条目；新增场景覆盖未变政策、拒绝重放、跨来源重复、每日/注册差异、真实变更、重置轮次与并发。辅助脚本的本地假 API 测试：`node --test .claude/skills/yangmao-review/evals/cli.test.mjs`。这只能验证工具行为，不能据此声称模型场景全部通过。

仓库副本是本项目权威。用户要求同步中央库时，先备份中央库旧包，再同步整个 `SKILL.md`、scripts、references、evals，并逐文件核对 SHA-256；不要只复制正文，也不要复制凭据、生产数据或评测工作目录。同步技能不批准任何条目，也不等于部署 Worker。
